# Decisions

Append-only decision record. The "why" lives here; the full change history lives in git.

- [2026-09-11] D-01 — Adopt token-lean wiki workflow: one ticket page per work item, git as change history, script-generated index/log/decisions — because the spec+plan+ticket+index+log ceremony duplicated git and burned tokens on every session and every feature
- [2026-09-12] D-02 — Full-width custom <button> rows need !important on width/margin/padding — Nextcloud core button:not(.button-vue, [class^="vs__"]) rules outscore CSS-module classes
- [2026-09-12] D-03 — Reuse list create/update endpoints for purchases (finalTotal + isFinished + purchaseDate) — because the OCS API already supports them, so the feature is frontend-only and needs no schema migration
- [2026-09-12] D-04 — Compute purchase total from all item prices client-side instead of the server totalPrice — because the server totalPrice only sums checked items and the web app has no check UI yet
- [2026-09-12] D-05 — Auto-create the store on save when the typed store name is unknown — because the purchase store field is an editable select for Android PurchaseDialog parity
- [2026-09-13] D-06 — Store the dashboard widget layout in localStorage instead of the server DB for now — because widgets are non-critical and easily re-created, and persistence lives behind a composable so it can move to the backend later
- [2026-09-13] D-07 — Compute all dashboard spending totals server-side via one range endpoint — because the client must not download all lists and paged history is planned
- [2026-09-13] D-08 — Dashboard spending sums finished lists by created_at, excluding isIncome and isSubscription — because that reflects actual expenses and keeps income/subscription views separate
- [2026-09-13] D-09 — Inject the app version through PageController + templates/index.php data attribute instead of a new endpoint — because info.xml stays the single source of truth with no extra API
- [2026-09-14] D-10 — Run receipt OCR server-side against the active LLM profile — because API keys are stored encrypted server-side and must never reach the browser
- [2026-09-14] D-11 — Strip receipt EXIF client-side via canvas downscale to 1024px/JPEG q0.6 — because it removes metadata and shrinks the upload, mirroring the Android scanner
- [2026-09-14] D-12 — Scan endpoint is read-only; a separate transactional commit endpoint writes store/list/product/item/price — because a partial save would corrupt the catalog
- [2026-09-16] D-13 — Merge duplicate products in one server-side transaction (concatenated aliases, re-pointed list items/prices, secondary deleted) — because a partial merge would corrupt the catalog and the concatenated aliases are what receipt matching relies on
- [2026-09-19] D-14 — Adopt Apache ECharts (tree-shaken, lazy-loaded Analytics chunk) for the Analytics charts — because emoji connector labels, center text and drilldown aren't provided by @nextcloud/vue and ECharts covers both donut and bar charts in one tree-shakeable dependency
- [2026-09-19] D-15 — Analytics aggregates at list level (bbml_lists.final_total + primary list category) — because it matches the D-08 dashboard semantics and the web app has no actual-price-rule setting yet
- [2026-09-19] D-16 — Top-5 store/list bars are horizontal — because long names stay readable and the category axis doubles as the legend
- [2026-09-20] D-17 — Default categories use fresh random UUIDv4 per user stored via the existing batch endpoint; cross-user sharing will map by link/alias instead of shared ids — because categories are owner-scoped personal taxonomy and identical cross-user ids are neither achievable for existing data nor safe (ownership, language, deletion)
- [2026-09-20] D-18 — POST /api/categories/batch accepts onlyIfEmpty; when set the server skips a non-empty account and derives ids deterministically as UUIDv5(owner:tempId) so concurrent default-category initialization converges on the primary key instead of creating duplicate sets — because the client-side pre-check cannot serialize two browser tabs
- [2026-09-21] D-19 — Analytics byCategory splits each finished list's final_total across its items' product categories (proportional, fallback to the stored list category when a list has no priced items) — because attributing a whole list to one pseudo-primary junction row (ordered by random UUID) collapsed multi-subcategory receipts under a single fake child and broke the drilldown
- [2026-10-02] D-20 — List sharing uses an access layer over the owner-scoped tables (bbml_list_shares + bbml_catalog_shares) instead of copying rows — because the vision requires live-propagating edits between the guest's and owner's catalogs
- [2026-10-02] D-21 — Share state lives in bbml_list_shares (list ACL) + bbml_catalog_shares (per-item guest→owner grants); revoking is soft (status=revoked) so the guest keeps a name-only placeholder — because hard deletes would lose the greyed-out placeholder the vision requires
- [2026-10-03] D-22 — Owner list share mark derives from an active-share lookup (hasShares) instead of a denormalized count — because the share table is already the source of truth and share changes flip the flag without a migration; editing a share reuses the idempotent POST /api/lists/{id}/shares upsert instead of a new endpoint
- [2026-10-03] D-23 — Use an addOnly flag (default false) instead of showShares (default true) for the share dialog — because Vue casts an absent Boolean prop to false, so a true default is impossible
- [2026-10-03] D-24 — Validate a share recipient with IUserManager::userExists server-side (422, localized) — because free-text UIDs previously created orphan shares for non-existent users; the frontend surfaces the OCS message
- [2026-10-03] D-25 — List-share catalog visibility is owner-scoped but guest→owner publishes grant only the specific item — because a single published product must not expose the guest's whole catalog, matching the per-item bbml_catalog_shares design
- [2026-10-03] D-26 — Revoked list shares serialize a name-only placeholder (no store/categories/flags) — because the guest keeps only the name to render the greyed-out row
- [2026-10-03] D-27 — Deleting a product revokes its catalog grants and deleting a list removes its share rows, both inside the delete transaction — because stale grants/shares otherwise leak visibility and accumulate
- [2026-10-13] D-28 — Add explicit kind + is_active columns to bbml_lists (backfilled from legacy flags) instead of deriving list type on the fly — because the To Buy redesign needs a stable discriminator for the active list, the status filters and the purchase-picker exclusion
- [2026-10-13] D-29 — To Buy items are plain text: bbml_list_items.product_id becomes nullable and the name lives in custom_name with quantity 1.0 and no price — because To Buy must never create or link catalog products
- [2026-10-13] D-30 — Exactly one active To Buy list, switched by an atomic deactivate-all + insert transaction (POST /api/lists/to-buy) — because a dangling is_active flag would break the To Buy screen and widget
- [2026-10-13] D-31 — To Buy auto-check after a purchase runs server-side against the active LLM profile — because LLM API keys are stored server-side and must never reach the browser
- [2026-10-13] D-32 — The To Buy dashboard widget stays client-side in localStorage, extending D-06 — because widget layout is already client-persisted and To Buy data comes from the existing list APIs
- [2026-10-13] D-33 — Backfill existing non-finished/non-archived/non-income/non-subscription lists to kind=NEED_TO_BUY, normalize archived lists to finished/kind=PURCHASE, and convert their items to plain text (custom_name from the product name, product_id NULL, qty 1, no price/discount) — because there is no production data yet and Android parity drops catalog links/prices for To Buy items
- [2026-10-13] D-34 — Purchase imports land in dedicated inbox tables (bbml_purchase_imports + items + categories) and only become bbml_lists on approval — because the phone sends raw names with no mapping and the import must stay reviewable, replaceable and auditable.
- [2026-11-09] D-35 — The client's per-list upload UUID is the dedupe key and the approved bbml_lists id — because resends must be idempotent and the contract requires both apps to share the list identity.
- [2026-11-09] D-36 — AI mapping only pre-fills suggestions and never approves — because catalog creation must be user-reviewed and hallucinated ids must not write data.
- [2026-11-12] D-37 — Remove archive mode entirely and never introduce in-store mode, matching Android: drop the `archived` status/label and migrate legacy archived lists to finished/PURCHASE — because both modes were deleted in the Android redesign and keeping them would break parity.
- [2026-11-12] D-38 — To Buy auto-check is gated only on an active LLM profile, with no separate consent prompt — because Android deliberately removed the consent gate (the analytics consent covers the AI Assistant only).
- [2026-11-12] D-39 — Copying a To Buy list preserves kind=NEED_TO_BUY, copies items as plain text and leaves the copy inactive — because only POST /api/lists/to-buy may switch the active list (Android parity).
- [2026-11-13] D-40 — Creating an LLM profile activates it when no profile is active — because a configured profile should be usable for AI suggestions without a separate selection step.
- [2026-11-13] D-41 — Import AI falls back to the only configured profile when none is active — because legacy installs can have a single inactive profile and a configured profile should still be usable.
- [2026-11-13] D-42 — Import AI matching stays user-triggered: the review explains that Suggest maps products and categories, and never calls the LLM on open — because auto-running would overwrite deterministic exact/barcode/alias matches and could clobber edits during the slow request
